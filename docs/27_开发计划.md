# 开发计划

版本：0.2 · 2026-10-01  
主责：先做哪一段、做到什么就能进入下一段。不改 `01`–`25` 的规则。完成与否用 `26` 的用例说话。

## 1. 起点

仓库里有这套文档、文档阅读器生成脚本和经济期望值手算（`tools/econ_handcalc.py`），还没有 Unity 工程，也没有 `content/` 表。第一段工作是把 `04` 和 `05` 变成能加载的 JSON，而不是先做开放地图。

## 2. 落地原则

- 先纯函数，再场景。成色、窗口、天气灾在没有模型时就要能测。
- 一条酒从米到柜上，比三块田同时长得好看更优先。
- 首发关闭的篇章、活动、拜访、支付不排进 0.1 的日程。
- 手感问题改表和表现，不在场景脚本里写第二套公式。

## 3. 里程碑

| 代号 | 名称 | 退出条件 |
|---|---|---|
| P0 | 契约 | `content/` 通过 `05` §4 的校验，开局状态与 `04` §1.1 一致 |
| P1 | 纯函数 | `26` 的 Q1–Q23 在无 Unity 依赖的测试里通过 |
| P2 | 院壳 | 一个灰盒院子能开坊、推进、收工，离屏批次照样扣时 |
| V | 首日 | `26` 的 F1–F5、F7 走通：搅开局那缸，蒸开局那批，卖出一瓶，看到三行日结 |
| P3 | 田与天 | 三块田从 G0 到收割，雨和暑会降品，Q10、Q11、Q19、F6 通过 |
| P4 | 蒸甑 | 特写三条参数写入瑕疵和形态档，时间在特写中暂停 |
| P5 | 前柜 | 客人按 `08` 买或离开，批购能接、能交、能逾期 |
| W | 首周 | 连续 7 日，含一个圩日；甜酒酿能在圩日前上柜 |
| P6 | 人与等级 | 阿禾自动搅缸、阿青两块一起割、委托三件、2 级能做清酒 |
| P7 | 发布门 | `26` §1 全部满足，帧率有一台机器的记录 |

P0 到 P7 是 0.1 的范围。夜泉、另外三套风格、活动、拜访、支付不插入这些里程碑。

## 4. 各段要点

### P0–P1

JSON 与 Domain 使用同一套 ID。测试失败时先对 `04`，不要在测试里把期望值改成「看起来差不多」。

### P2 与 V

灰盒用方块表示田、甑、缸、柜。V 不要求饭床形态键，但蒸饭命令必须能写 `handmade`。开局批 A 的窗口要从第 1 个可玩时刻就亮着，否则首日引导不成立。

### P3–P5

田的模型可以先只有 G0、G5 两档，但数据层必须有 G0–G6。前柜先用列表成交，酒液颜色可以后补。离开原因必须是 `08` 的那几句之一。

### W 与 P6

首周用来看甜酒酿和米酒会不会互相卡住窖位和现金。若 7 日内一件都卖不出，先查客流和开局库存，不先加新客人。  
P6 的第三个人手是伙计，不是好友。

### P7

发布门不包含移动端和主机。记录写进构建说明，不改文档里的目标帧率。

## 5. 0.1 之后

按 `01` §7 的顺序：暖窑与白瓷、常驻旧事的其余句子、夜泉。每一项启用前先把默认关闭的开关改成数据行，并补 `26` 的隔离用例，避免首发包被带着打开。

## 6. 本文不改的规则

工期、人数、外包不在这里许诺。简案里的 18–30 个月是全平台量级，不是这 10 个里程碑的日历。0.1 的日历以 P7 的用例为准，做完再估下一季。
